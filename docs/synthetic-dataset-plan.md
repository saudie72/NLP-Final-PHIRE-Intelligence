# 9. Synthetic dataset plan

The dataset will be generated by a script (`scripts/make_synthetic.py`, built in a later step after approval).
It reproduces the PHIRE export's **layout and writing style** without copying any real content.

## Outputs (`data/synthetic/`)

| File | Rows | Columns | Purpose |
|---|---|---|---|
| `phire_train.xlsx` / `.csv` | ~1,000 | 16 PHIRE columns + `Issue Area` + `Recurring Group` | Model training and cross-validation |
| `phire_test.xlsx` / `.csv` | ~250 | same | Final evaluation, used once |
| `phire_demo_export.xlsx` | ~250 | the 16 PHIRE columns only | What a user uploads in the demo; looks exactly like a PHIRE export |

## How tickets are generated

1. **Pick a module** with weights that reflect a typical county HCM-heavy workload (HR, PY and TL most common,
   then GL, AP, PO, BN, AM, others).
2. **Pick an issue area** from module-specific proportions (for example `SEC` is mostly Security and `PT` is
   mostly Administration; business modules are about 50% Functional, 25% Technical, 12% Security, 13% Administration).
3. **Fill a template** with module vocabulary: real PeopleSoft page, process, report and field names, TRCs,
   ChartFields, error messages, plus fictional departments, business unit codes, dates and user IDs.
4. **Add realistic noise:** optional openers ("Business Unit = XX / PPE date"), closers ("See attachment",
   steps to reproduce), line breaks, and references to earlier issue numbers.
5. **Fill structured columns:** Priority (H/M/L), Issue Type, Status (closed tickets get Closed Date and a
   Resolution Code), Aging, Due Date (Open Date + 5 / 10 / 20 days by priority), CR for most technical and
   enhancement tickets, fictional analyst and developer names.

## Train/test separation

- Train and test descriptions come from **two separate phrasing banks** (A and B). Same PeopleSoft vocabulary,
  different sentence structures and wording, so the test measures generalization, not template memorization.
- Example: train says "Processes submitted for Time Administration have stayed in Queued status"; test says
  "Nothing has run on the scheduler since 11/03/2026; everything sits in Queued."

## Recurring groups (for similarity and clustering evaluation)

- About **24 recurring issues**, each with fixed key details (module, page, process, department, BU).
- Each appears 3–6 times in training and 1–2 times in testing, spread over time, sometimes with
  "this has been done before, reference IN…".
- The `Recurring Group` column (`RG-01` …) is the ground truth for precision@5, duplicate detection and
  clustering scores.

## Fictional identity rules

- Names come from a fixed list of fictional first and last names; user IDs are derived from them.
- Departments are generic county departments; no real person, ticket or CR number is used.
- All synthetic files are deterministic (fixed random seed), so anyone can regenerate the same data.

## Limitations

- Template-generated text is cleaner and more consistent than real tickets, so real-world accuracy will be
  lower than synthetic test accuracy. The results page will say so.
- Label proportions and status lists are assumptions until confirmed (see [README](README.md)).
